Оркестратор **активно запрашивает задачи** из внешней системы (task queue) до тех пор, пока на сервере есть доступные ресурсы для запуска агентов. Когда агент завершает работу и освобождает ресурсы, оркестратор немедленно запрашивает новую задачу.

**Модель pull (вытягивание задач):**
- Оркестратор постоянно мониторит доступные ресурсы памяти
- При наличии свободной памяти оркестратор запрашивает следующую задачу из очереди
- Получив задачу, оркестратор запускает агента, передавая ему ID задачи при создании контейнера
- Агент НЕ получает задачи самостоятельно - ID задачи передаётся через переменную окружения 


Задача выполняется в рамках контекста.
Одна задача - один контекст.
Один контекст - один агент. Несколько агентов не могут работать с одним контексом одновременно.

Когда поступает новая задача, оркестратор должен проверить требуется ли для задачи контекст. При необходимости ресурсы контекста должны быть созданы орекстратором. 

Агент не имеет обратной связи с оркестратором для получения задач. Оркестратор передаёт ID задачи при запуске агента через переменную окружения.

Если для задачи не требуется контекст, то оркестратор запускает нового агента без контекста, передавая ID задачи при старте.

Если для задачи требуется контекст, то нужно проверить используется ли он. Если контекст свободен, оркестратор создаёт новый агент с привязкой к требуемому контексту и передаёт ID задачи при запуске. Если контекст занят (есть работающий агент), задача помещается в очередь для этого контекста и будет обработана после завершения текущей задачи. В хранилище сохраняется привязка агента к контексту и время привязки.

Каждый агент обрабатывает ровно одну задачу (ту, что передана при запуске), после чего завершает работу.

## Контекст

Контекст - это совокупность сведений сохраняющихся за пределами агента. На данный момент контекст включает:

- связанный с контекстом volume подключаемый к папке /repos

## Очереди задач

Оркестратор запрашивает задачи через **HTTP REST API** из внешней системы.

**Стратегия pull через REST API:**
- Оркестратор выполняет HTTP запросы к внешнему API для получения задач
- Запрос новой задачи происходит:
  - При старте оркестратора (заполняет все доступные ресурсы)
  - При завершении любого агента (освобождение ресурсов)
  - Периодически, если очередь была пуста, но могли появиться новые задачи
- Если контекст занят, задача откладывается в локальную контекстную очередь оркестратора

## Обработка сбоев

**Механизм восстановления при неожиданном завершении агента:**

Если агент завершил работу неожиданно (crash, kill, ошибка), задача не будет отмечена выполненной в API. После истечения таймаута задача автоматически становится доступной для повторного получения, и оркестратор сможет запросить её снова через HTTP REST API.

**Принцип работы:**
- Задача в API имеет таймаут выполнения
- Пока задача выполняется, она "заблокирована" для других запросов
- Если агент не отметит задачу выполненной в течение таймаута, блокировка снимается
- Оркестратор при следующем запросе получит эту же задачу и запустит нового агента
- Оркестратор должен очистить ресурсы "мёртвого" агента (контейнер, контекст)

**Важно:** Задачи, переданные API оркестратору, считаются "ожидающими выполнения" и больше не выдаются из API до наступления таймаута. API гарантирует, что одна задача не будет выдана дважды одновременно - можно не беспокоиться о дублировании задач.

## Проблемы 

- необходим механизм отслеживания завершения работы агента для запуска следующей задачи из очереди
- нужен точный мониторинг доступной памяти и потребления каждым агентом
- при нехватке памяти задачи накапливаются в очереди - нужны алерты и метрики
- требуется мониторинг "зависших" агентов для своевременной очистки ресурсов

## Ограничения по ресурсам

Одновременно могут выполняться столько агентов, сколько может быть размещено в оперативной памяти сервера. Оркестратор должен отслеживать доступную память и управлять количеством одновременно работающих агентов.

**Стратегия управления:**
- Оркестратор постоянно запрашивает задачи пока есть доступная память
- Если памяти недостаточно, оркестратор останавливает запросы новых задач
- При завершении агента:
  1. Освобождается память
  2. Оркестратор проверяет локальные контекстные очереди
  3. Если локальных задач нет - запрашивает новую задачу из внешней очереди
- Необходимо установить лимит памяти на контейнер агента для предсказуемого планирования
- Оркестратор отслеживает: (доступная_память >= память_на_агента) → запросить новую задачу

## Модель работы (Pull-based)

**Цикл запроса задач:**
1. Оркестратор **проверяет доступную память**
2. Если память доступна → **выполняет HTTP REST API запрос** для получения задачи
3. Если задач нет (API вернул пустой ответ) → ждёт и повторяет через интервал
4. Получив задачу, **определяет требуется ли контекст**
5. Если контекст не нужен → **запускает агента** с ID задачи
6. Если контекст нужен:
   - Проверяет свободен ли контекст
   - Если свободен → запускает агента с ID задачи и контекстом
   - Если занят → добавляет задачу в локальную контекстную очередь
7. После запуска возвращается к шагу 1 (пока есть память)

**При завершении агента:**
1. Агент завершается после выполнения задачи (отмечает задачу выполненной в API)
2. Освобождается память
3. Оркестратор получает событие завершения (Docker events / webhook)
4. Если агент работал с контекстом:
   - Проверяет локальную очередь для этого контекста
   - Если есть задачи → запускает агента для следующей задачи
   - Если очереди нет → освобождает контекст
5. Запускает цикл запроса новых задач через HTTP REST API (шаг 1)

**При неожиданном завершении агента:**
1. Оркестратор обнаруживает падение контейнера (Docker events)
2. Освобождает память
3. Освобождает контекст (если был привязан)
4. Задача НЕ отмечена выполненной в API
5. После истечения таймаута задача становится доступна для повторного получения
6. Оркестратор запросит её при следующем цикле запроса задач

**Принцип:** Оркестратор максимально утилизирует ресурсы, постоянно запрашивая задачи через HTTP REST API.
