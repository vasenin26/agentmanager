# Agent Token Configuration

## Общий токен для всех агентов

В оркестраторе используется **один общий токен** для аутентификации всех агентов. Это упрощает управление и обеспечивает единообразный доступ к API.

## Конфигурация

### Переменная окружения

```bash
AGENT_API_TOKEN=your-shared-agent-token
```

Эта переменная должна быть установлена в окружении, где запускается оркестратор.

### Значение по умолчанию

Если переменная `AGENT_API_TOKEN` не установлена, используется значение по умолчанию:
```
default-agent-token
```

**Важно:** В production окружении обязательно установите собственное значение токена!

## Как это работает

1. **При старте оркестратора**: 
   - Загружается значение `AGENT_API_TOKEN` из переменной окружения
   - Токен сохраняется в `OrchestratorService`

2. **При запуске агента**:
   - Оркестратор создает `ConfigOptions` с общим токеном
   - Токен передается в `AgentService.StartAgentForTask()`
   - Агент запускается с переменной окружения `API_TOKEN={token}`

3. **Использование агентом**:
   - Агент использует `API_TOKEN` для аутентификации с внешними API
   - Все агенты имеют одинаковый токен

## Пример конфигурации

### Docker Compose

```yaml
environment:
  - AGENT_API_TOKEN=my-secure-token-123
```

### .env файл

```bash
AGENT_API_TOKEN=my-secure-token-123
```

### Прямой запуск

```bash

./agentmanager
```

## Отличия от HTTP API

### Оркестратор (Pull-based)
- **Один токен** для всех агентов
- Токен задается через `AGENT_API_TOKEN`
- Управляется централизованно оркестратором

### HTTP API (Push-based)
- **Уникальный токен** для каждого агента
- Токен передается в запросе `POST /orchestrator/start-agent`
- Управляется клиентом API

## Безопасность

### Рекомендации

1. **Используйте криптографически стойкий токен**
   ```bash
   # Генерация токена
   openssl rand -base64 32
   ```

2. **Храните токен в секретах**
   - Используйте Docker secrets
   - Используйте Kubernetes secrets
   - Не коммитьте токен в Git

3. **Ротация токенов**
   - Периодически меняйте токен
   - При изменении требуется перезапуск оркестратора
   - Работающие агенты продолжат использовать старый токен

### Что делать при компрометации

1. Немедленно измените `AGENT_API_TOKEN`
2. Перезапустите оркестратор
3. Дождитесь завершения работающих агентов или остановите их
4. Новые агенты будут использовать новый токен

## Логирование

При старте оркестратора токен **НЕ** логируется в целях безопасности. В логах вы увидите:

```
INFO    Orchestrator started
```

Без раскрытия значения токена.

## Проверка конфигурации

Чтобы убедиться, что токен передается агентам:

1. **Проверьте переменные окружения оркестратора**:
   ```bash
   docker exec <container-id> env | grep AGENT_API_TOKEN
   ```

2. **Проверьте переменные окружения агента**:
   ```bash
   docker inspect <agent-container-id> | jq '.[0].Config.Env'
   ```
   
   Должна присутствовать строка: `"API_TOKEN=your-shared-agent-token"`

## FAQ

### Почему один токен для всех агентов?

- **Упрощение управления**: не нужно генерировать уникальные токены
- **Единый источник**: все агенты используют одинаковую конфигурацию
- **Централизованное управление**: токен контролируется оркестратором

### Можно ли использовать разные токены для разных агентов?

В текущей реализации нет. Все агенты используют общий токен. Если требуется разграничение доступа, используйте:
- HTTP API для запуска агентов с уникальными токенами
- Дополнительную аутентификацию на уровне внешнего API

### Что происходит если токен не установлен?

Используется значение по умолчанию `"default-agent-token"`. Это подходит для разработки, но не для production.

### Как изменить токен без простоя?

В текущей реализации требуется перезапуск оркестратора. Для zero-downtime обновления можно:
1. Настроить внешний API для приема двух токенов (старого и нового)
2. Обновить `AGENT_API_TOKEN` на новый токен
3. Перезапустить оркестратор
4. Дождаться завершения старых агентов
5. Убрать старый токен из внешнего API
